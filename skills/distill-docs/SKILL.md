# /distill-docs file1 [file2 ...]

归档规划文档：从指定文件中提取值得长期保留的业务知识，沉淀到项目文档中，然后删除原文件。

待归档文件: $ARGUMENTS

## 核心原则

代码是实现细节的 source of truth，文档只记录代码无法传达的知识。对每条内容问：

**"删掉它会导致未来的开发者（或 Claude）犯错吗？"**

如果不会——不沉淀。

### 保留（代码无法推导）

- **设计约束和 why**：架构决策背后的原因（如"决策与执行分离是为了满足 ATP SDK 单线程约束"）
- **跨文件全貌**：需要读多个文件才能拼出的信息（如跨线程安全矩阵）
- **生产配置/运维知识**：影响部署的配置值、内核参数、环境要求
- **当前状态标注**：待办事项、已知限制、待他人配合的事项
- **外部依赖约束**：第三方 SDK 的线程安全要求、API 限制等

### 不保留（有更权威的来源）

- **调用链、函数签名、锁用法** → 读代码
- **方案对比和论证过程** → 结论已体现在代码或最终文档中
- **git 可查的信息** → git log / git blame
- **调试过程和临时状态** → 修复在代码里，commit message 有上下文
- **标准库/框架用法** → 通用知识

### 文档风格

- 表格优于散文（跨线程安全矩阵、CPU 布局等用表格）
- 约束用要点列表，不展开实现细节
- Link, don't copy — 引用而非复制详细内容

## 流程

### 1. 读取与分析

并行读取所有待归档文件，同时读取可能的目标文档（`docs/` 目录结构），理解已有文档的覆盖范围。

检查是否有其他文档引用了待归档文件（grep 文件名），确保删除后不留下断链。

### 2. 分类提取

对每个待归档文件，逐段判断：

- **沉淀** → 标注目标文档和位置
- **丢弃** → 标注原因（代码可推导 / 方案论证过程 / 已有覆盖）

### 3. 与用户对齐

向用户报告：
- 计划沉淀到哪些文档的哪些章节，内容摘要
- 计划丢弃的内容及原因
- 是否有断链需要处理

等用户确认后再执行。如果用户对某条判断有异议，按用户意见调整。

### 4. 执行变更

- 将提取的内容写入目标文档（编辑已有章节或新增章节）
- 删除原始规划文件
- 如有断链（其他文档引用了被删文件），更新引用

### 5. 验证

变更完成后，再读一遍修改过的目标文档，用核心原则自检：
- 新增内容是否有代码无法推导的信息？
- 是否保持了简洁（表格 > 散文，约束 > 实现细节）？
- 是否与目标文档已有内容风格一致？
